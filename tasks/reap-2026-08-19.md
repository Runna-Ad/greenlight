## TOP PRIORITY

### P1 — Sync import is an N+1 waterfall → Vercel timeout risk `[perf, verified]`
`src/app/(app)/[cliente]/sync/import.ts:138-322` — `for (const row of rows)` with ~7 sequential DB round-trips per row, no batching, no `Promise.all`, no `maxDuration`. A 50-100 row sheet sync = 350-700 sequential round-trips ≈ 20-55s in one server action → default Vercel function limit timeout, and a blocking UI wait regardless. The correct batched pattern already exists one dir over: `briefs/nuevo/actions.ts` builds a payload and does one `rpc_crear_brief`.
**Fix:** batch-prefetch (`.in(...)`) existing staged_rows/families/sibling-variants, compute in JS, bulk-insert; or move into an RPC. **Also (P1b):** the `staged_rows` dedup-marker upsert (`import.ts:301-318`) drops its `{ error }` — if it fails, the next sync re-imports the row → duplicate tasks in prod. Check that error.

### P2 — Portal "request a change" flow is mouse-only `[a11y CRITICAL ×2 + UI/UX, convergent, verified]`
`src/components/tarea/campo-lectura.tsx` — the client Portal's core interaction (select text → "Pedir cambio aquí"; hover a mark → see/remove the pinned change) is wired **only** to `onMouseUp` (capture) and `onMouseEnter/Leave` (detail card). No `onKeyUp`/`selectionchange`, no `onClick`/focus path. The editor's sibling `campo.tsx` deliberately has all three (`onSelect`+`onMouseUp`+`onKeyUp`) plus a click-to-open pin button — the fix pattern exists in-repo.
- Keyboard-only client: cannot request a change at all (can only "Aprobar").
- Touch client (Portal is explicitly mobile-important): hover cards can't open on tap; text-selection→button is unreliable (mobile browsers need `selectionchange`, not `mouseup`).
**Fix:** add `selectionchange`/`onKeyUp` capture + a click/focus affordance to open the card (mirror `campo.tsx`). **Recommend a 5-min live mobile-device check to confirm the touch-selection behavior.**

## SERIOUS — by theme

### A. Destructive actions with no confirmation `[UI/UX, verified]` — app already has the two-step pattern (`correcciones/panel.tsx`)
- `documento-tarea.tsx:166` → `actions.ts:453 borrarPlano` — single click hard-`DELETE`s an entire plano (scene + all fields + refs), no confirm, no undo.
- `portal-acciones.tsx` — client "Aprobar" fires with zero confirm; sticky-bar mistap on mobile → `delivered` + emails the team, no undo in UI.
- `referencias-plano.tsx:252` — reference image delete: single click, hard delete, X only visible on hover.

### B. Corrections-lifecycle data integrity `[DB, verified]`
- **S1** `comments.target_fila_id` has **no FK** (polymorphic via `target_tabla`) and isn't covered by any cascade. `rpc_import_planos(...,'replace')` deletes planos and re-inserts with fresh PKs; `borrarPlano` deletes one. Any affected correction's target is orphaned → it still counts unresolved so `correction_next_round` never auto-closes the round, and the field UI can't render/confirm it (only approve-auto-resolve or manual discard clears it). A `'replace'` import orphans ALL of that idea's plano-anchored corrections at once. **Fix:** BEFORE DELETE trigger to resolve/delete matching comments, or block delete with open corrections, or remap by `orden` instead of wiping PKs.
- **S2** `tablero/actions.ts:149 rpc_task_request_changes` inserts a `correction_request` with **null categoria + null target**; `evaluacion.ts:176` skips null-categoria rows and can't attribute a null-target author. → Corrections requested from the **board card / mi-trabajo** never appear in rúbrica scoring (under-counts specialists, inflates scores) and render location-less in the panel. The task-detail flow requires a category. **Fix:** make `rpc_task_request_changes` record a categoria (or retire the board free-text path), and decide if null-target corrections should score.

### C. Concurrency races `[correctness + DB, verified pattern]` — both low-probability on a small team
- `notif-email.ts:21-91 dispatchPendingEmails` — SELECT pending → send → UPDATE 'sent' with no atomic claim/lock. Two overlapping runs (lead clicks Aprobar then Enviar quickly; two people act at once) both send the same email. "Idempotente" comment is aspirational. **Fix:** atomic claim `UPDATE ... SET status='sending' WHERE id=ANY(...) AND status='pending' RETURNING id`, send only returned rows.
- **S3** round-numbering read-modify-write: `correction_next_round` is read then stamped in a separate statement (`rpc_client_submit_changes:82-85`, `rpc_add_correction:74`, `rpc_task_request_changes`) with no `FOR UPDATE`/advisory lock → a concurrent confirm+add can mis-group a new correction into a just-closed round. **Fix:** `SELECT ... FROM ideas WHERE id=p_idea FOR UPDATE` or `pg_advisory_xact_lock` at the top of each round-stamping RPC.

### D. Performance (beyond P1) `[perf, verified]`
- `entregas/page.tsx:29-53` — `ideas` unbounded (grows forever), and `briefs`/`idea_assignments` fetched **across all clients** unscoped, every page view. **Fix:** scope with `.in(...)` from the returned ideas; add date window/pagination.
- `performance/data.ts:31-47 cargarWorkload` — `idea_assignments`/`ideas`/`briefs`/`clients` all fetched in full, filtered in JS, on every request (`force-dynamic`). **Fix:** push `ESTADOS_ACTIVOS` filter into SQL.
- `referencias-data.ts:19-29 firmar` — one `createSignedUrl` HTTP call per reference image (parallelized but N round-trips) on every task-page + portal render. `@supabase/storage-js` ships batched `createSignedUrls(paths[])`. **Fix:** one batched call. (Also folds in the todo "deuda": `page.tsx` inline ref-signing → move to this helper.)
- `contexto.tsx:107-135 CorreccionesProvider` — context `value` + all callbacks recreated every render → any provider state change re-renders every `Campo`/`CampoLectura` in the doc (30+). `validar()` updates `veredictos` via `useState` with no `router.refresh()` → pure client re-render storm on "Validar cambios". **Fix:** `useMemo`/`useCallback`, or split `veredictos`/`validando` into a narrow context.
- `pegar-guion.tsx` (`"use client"`) → `@/lib/guion` → static `import { EMOJI } from "./emoji-map"` (3421 lines / ~96KB) ships in the task-editor client bundle for an occasional paste feature. **Fix:** lazy `await import("./emoji-map")` inside `emojificar()`.

### E. Error handling / resilience `[TS-safety, verified]`
- No `error.tsx` / `global-error.tsx` anywhere; `(app)/layout.tsx` awaits 4 calls with no try/catch → any throw = Next's generic unstyled crash screen (no Spanish, no recovery). **Fix:** add `(app)/error.tsx` + root `global-error.tsx` with a styled "algo salió mal" + retry.
- Systemic: ~44 read sites destructure only `{ data }`, folding a transient DB error into "no data." Root page-gating queries are the ones that matter: `tareas/[id]/page.tsx:54` (real task → 404), `tablero/page.tsx:23` (outage → "no hay tareas, sincroniza"), `soy.ts:47` (hiccup → silent identity logout). **Fix:** check `error` on the handful of root queries, route to a distinct error state.
- `sheet-sync.ts:328-347` — external Apps Script JSON cast (`body.tabs as ...`, `body.rows as ...`) with no shape validation → cryptic "undefined is not iterable" on drift (caught by caller, but opaque). **Fix:** `Array.isArray` guard + clear message.

### F. Accessibility (beyond P2) `[a11y, verified]`
- `campo-lectura.tsx:442` — the interactive correction card is `role="tooltip"` but contains Confirmar/Descartar/Quitar buttons; AT won't expose them. **Fix:** `role="dialog"`/`group`, manage focus.
- `panel-revisiones-cliente.tsx:85` — the client "jump to changed field" card is a `<div onClick>` with no `tabIndex`/`role`/`onKeyDown`; no keyboard path (the internal `panel.tsx` has a redundant "Ver" button — this new portal one doesn't). **Fix:** add a "Ver" `<button>` or make the card a real button. *(This is from the just-shipped portal work — quick fix.)*
- `referencias-plano.tsx:252` — delete X is `display:none` until `group-hover` (no `group-focus-within`) and 16×16px. **Fix:** add `group-focus-within:flex`, enlarge hit area.

### G. Security — app-layer authz (launch-hardening) `[security, verified crearBrief + sync]`
**The Portal cross-tenant boundary is correctly enforced** (every portal action runs `esDelCliente`; loaders verify slug). No High/Critical; no secret/injection/SSRF defect. The gaps are one class: **server actions that rely on the page-level role gate instead of re-checking role/ownership** — real holes the moment `AUTH_ENABLED` flips (a `"use server"` export is a public POST). Several sibling actions DO re-check, so it's an inconsistency.
- **MEDIUM** `sync/actions.ts` (`previewProjects`/`listProjects`/`getSyncMode`) + `sync/page.tsx` — no role check; returns raw sheet row content (unreleased concepts/copy); `listProjects` can enumerate all tabs → cross-client if the workbook is multi-client.
- **MEDIUM** `sync/import.ts:43 importRows` / `knownRows` — no role check; writes briefs/ideas/assets to any client by slug from attacker-controlled rows.
- **MEDIUM** `briefs/nuevo/actions.ts:37 crearBrief` — no `canCreateBrief` re-check (page has it); direct POST creates a brief + tasks and fires **real notification emails** to specialists.
- **MEDIUM** `admin/actions.ts:312/341/360` snippet create/edit/toggle — no `canAdmin`; a `scope='global'` **legal** snippet edit changes legal text across all clients' deliverables.
- **LOW** `admin/actions.ts` read actions (`listarEquipo` etc.) — no role check; exposes team roster + emails + slack ids, cross-client activity feed.
- **LOW** `tareas/[id]/page.tsx:54` — idea loaded by `id` only; `[cliente]` slug never verified against the resource (latent IDOR; not exploitable today since team roles see all clients).
**Fix:** add the same `getViewAs()` + `can*` re-check these actions' siblings already use. **Prioritize the two with real side effects even in the open window: `crearBrief` (emails) and the global legal snippet edit.**
